**The framework's own changelog — not a project's.** A project's `CHANGELOG.md`
records what *it* shipped. This records what the *framework* gained, so a
project that adopted it in June can be told, in one screen, what it has been
missing since.

The version here is the one in [`VERSION`](VERSION). It is written into each
project as `.docket-version` when `docket-update.py` runs, and the dashboard reads
it back. That is the whole mechanism: **one number in the skill, the same number
stamped in the project, and a changelog that explains the distance between
them.**

## 4.2.0 — 2026-09-21

The capture inbox was a different file depending on whose machine wrote it last, and a
session working on the framework wrote into a project.

- **`docket-server.py` names its encoding on every inbox call.** Without `encoding=`,
  Python uses `locale.getpreferredencoding()` — **cp1252 on Windows, UTF-8 on a Mac**. So
  `docket-inbox.md` in a shared folder became two formats: creating one on Windows raised
  `UnicodeEncodeError` outright, and reading a Mac-written one there died on `0xb7`, a `·`.
  Four calls, now all encoded, with `newline=""` so the line endings stop drifting too.
- **Found in a project, fixed here — which is the point.** That project had patched **its
  own copy** of `docket-server.py`. The updater leaves an edited file alone forever, so the
  patch pinned that project to it and cut it off from every later fix, while every other
  project kept the bug. **One project silently fixed, everyone else still broken.**
- **`SKILL.md` — *Working ON the framework? Do not write into a project.*** The rule has two
  halves: a framework session fixes the framework and the project takes it with an update,
  never the reverse; and a question belongs to whoever owns the subject, with the test being
  *would this still matter to that project if this repository were deleted tomorrow?*
- **`Q-11`** — *Manning cannot report a framework bug at all.* Moved here from that project,
  where it had been filed by mistake. The master is on one machine with no remote, so half
  the people using this framework have no reporting route — which is `LE-25`'s failure mode
  exactly: the flaw gets silently worked around.

**Do:** projects on an older release take this with `./scripts/docket.sh --update --apply`.
A project that hand-patched `docket-server.py` will be reported as edited and left alone —
diff it against this version and take this one, since the fix is now here.

## How to write an entry

Every release gets a section, **in the same turn it ships**, and the shape is
parsed rather than merely read — `docket_version.py` turns it into the
"what's new" the updater prints and the dashboard shows:

```markdown
## X.Y.Z — YYYY-MM-DD
One line saying what the release is for.

- What a project gets. Written for somebody deciding whether to update,
  not for whoever wrote it.

**Do:** anything the update cannot do for itself, as a command.
```

The example uses `X.Y.Z` rather than a plausible version **on purpose**. With a
real number there, a scripted edit that inserts the next release by replacing the
newest heading matches the *example* first and files the entry inside this code
fence — where the parser, correctly, ignores it. The release then ships with a
changelog that mentions it nowhere. That happened.

The heading must be `## MAJOR.MINOR.PATCH — YYYY-MM-DD`. Bullets are the
changes. A `**Do:**` line is a manual step: the updater prints it after
applying, because a file copied into place is not the same as a thing that has
taken effect.

**Bump the number for anything a project would want.** A framework version is
not a marketing decision — it is the key the updater uses to work out what a
project is missing, and a change that ships without one is a change no project
will ever be told about.

- **major** — a project must do something by hand or it breaks
- **minor** — new capability: a script, a page, a gate
- **patch** — a fix to something already shipped

## 4.1.1 — 2026-09-21
**A brand-new project's `check-docs.sh` could never pass.** Fixed.

- `check_framework_reports.py` and `check_ships.py` are deliberately never
  shipped to a project — and both were called, unguarded, from the
  `check-docs.sh` that **every fresh install copies verbatim**. Each failed with
  `can't open file`, each set `fail=1`, so the first thing a new adopter runs
  was broken on arrival (`LE-33`). Both are now behind `if [ -f .docket-master ]`.
- **Existing projects were never affected**, because `check-docs.sh` is never
  replaced — its gates are the project's own. The defect lives only on the

  Same blind spot as `4.1.0`, one day apart.
- **Found by another project, not here.** `tts2` hit it while adopting, reported
  it with the mechanism `3.19.0` added, and worked around it locally so its own
  check could pass. It is the first framework flaw this framework was told about
  rather than noticing.

**Do:** if you adopted `4.0.0` or `4.1.0` into a *new* project and guarded those
two lines by hand, take this update and remove your guard — it is in the shipped
file now.


## 4.1.0 — 2026-09-21
The viewer's document label sat on top of *Expand all* and *Collapse all*.

- **Two sticky elements were both pinned at `top:0`** — the bar with the
  project name and controls, and the label naming the document you are reading.
  The label is opaque and had `z-index:5`, so it painted over the controls.
- **It could not be seen from here.** The overlap is proportional to the
  document name, and the master's names are short enough never to reach the
  controls. **The framework's own viewer is the one place this defect cannot
  appear**, and it is where the viewer gets looked at. Reported from RainZips.
- **Fixed three times before it was fixed** (`LE-32`): offsetting the label
  below the bar was not enough; *measuring* the offset instead of guessing it
  was not enough either — the first reading was 54px against a bar that settled
  at 61, because the heading font had not loaded, which is the same bug with a
  number that looks deliberate. What settles it is making the bar paint above:
  it was `static` with `z-index:auto`, creating no stacking context, while a
  sticky label creates one.
- The offset is now watched with a `ResizeObserver`, which covers the font load,
  the theme switch and the mobile breakpoint without knowing about any of them.
- **The check worth stealing:** `elementFromPoint()` at the button's
  coordinates, with a long label deliberately scrolled through it, must return
  the button. Not *do the rectangles overlap* — that was harmlessly true in
  several places. **Geometry describes the page; hit-testing describes the
  user.**

**Do:** update, then `./scripts/docket.sh --build` to regenerate the viewer. The
fix is in `build_docket.py`, so an existing `docs/docket.html` keeps the bug
until it is rebuilt.

  being to delete the file yourself.

**Do:** nothing beyond `4.0.0`'s corrected list.

## 4.0.0 — 2026-09-21
**`DOCS_LOCK.md` is retired.** A repository replaces it.

**Major because you have to act.** Two manual steps, and the first is not
optional — see `Do:` at the end.

**The update will not delete the file for you, and that is correct.** `RETIRED`
only removes a copy that still matches what was installed, and **a lock that was
ever used does not**: taking and releasing it is an edit, so every project that
actually followed the protocol has a modified copy. The updater reports it and
leaves it, which is the right refusal — it just means the deletion is yours.
(Verified on a real project rather than assumed; the first draft of this entry
claimed the removal was automatic and it is not — `LE-30`'s family, caught by
running it.)

- **It was never a mechanism.** `check-docs.sh` *printed* the holder and **never
  failed on it.** Nothing anywhere returned non-zero because a lock was held, so
  it could not stop anything by construction — which is this framework's own
  Rule 4 violated in its own house: *a disclaimer is not a mechanism.*
- **And it was measured: never once refused, in any project, in its whole
  life** — the same result `KAC` found for the board's per-path claims.
- **`LE-31` — how it hid.** It was performed diligently: taken and released
  about ten times in the session that retired it. **A rule that is never broken
  and a rule that is never checked produce identical evidence.** The only way to
  tell them apart is to ask what would happen if somebody broke it, and nobody
  asked for three months.
- **`check_git.py` replaces it** — it **warns, never fails**, while a project has
  no repository, and prints the one command that fixes it. What makes the
  2026-09-16 clobber survivable is being able to undo it, not being asked to
  take turns. Four of nine projects would warn today. It never runs `git init`
  itself: creating a repository unasked is not this framework's business, and
  publishing one is emphatically not (`GD`).
- **The board does not replace it**, despite appearances. `bbs` only exists
  during a Docket team run; the lock was for two ordinary terminal sessions,
  which nothing else covers. **Removing it accepts that risk rather than
  transferring it** — which is the right trade only because a repository makes
  the outcome recoverable.
- The retirement is clean: the printing block is guarded by
  `if [ -f DOCS_LOCK.md ]`, so removing the file silences it everywhere without
  touching a `check-docs.sh` the updater must never replace.

**Do:**

1. **Delete `DOCS_LOCK.md` yourself.** The updater names it and leaves it,
   because your copy differs from what was installed — which it does precisely
   because you used it.
2. **Edit your `CLAUDE.md`**, which is reported and never rewritten: delete the
   section telling sessions to take the lock.
3. If `check_git.py` warns, run
   `git init && git add -A && git commit -m 'the project as found'`.


## 3.20.1 — 2026-09-21
The console tells you when it is not running, instead of printing a browser
exception.

- **`could not run: TypeError: Failed to fetch`** is what the *What would
  change?* button printed when nothing answered. It says nothing about what
  happened or what to do, and the thing to do is one line. It now says **the
  console is not running**, names the address it tried, and gives the command
  that restarts it.
- **`KAR` — the console lives as long as its terminal, and that is the point.**
  Noticed on quitting a session and being asked whether to stop it too. **That
  prompt is the security model working.** The console runs an allowlist of
  project commands over `/api/run`, so one that outlived the session would be a
  long-lived local server with shell access that nobody is watching. It is
  deliberately not detached, not daemonised and not restarted for you.
- The cost is real and worth naming: **a browser tab left open goes dead
  silently**, and the first sign is a button that does nothing. That is a
  message problem rather than a lifetime problem, and it is fixed as one.
- `templates/CLAUDE.md` now says to mention this when handing over the URL.

**Do:** restart any running console to pick up the new message.


## 3.20.0 — 2026-09-21
A button on the console that reports what an update would change, and the fix
for a script that did not ship when `3.19.0` said it would.

- **"What would change?" on the version badge.** It runs the updater in report

  delivers it is a feature whose delivery is untested.*
- **`check_ships.py`** — master only — asserts every script is in exactly one of

## 3.19.0 — 2026-09-21
A project that finds a bug in the framework now has somewhere to put it, and the
master cannot ignore it.

- **`scripts/docket-report.py` ships to every project** (`KAQ`). One command,
  appends one line to the master's inbox, **edits nothing there**.
- **`scripts/check_framework_reports.py` — master only — fails
  `check-docs.sh` while a report sits unfiled.** Same shape as the answer

  underneath the work in hand.
- **Not reportable:** a preference, or something this project wants and the
  framework lacks. Only a thing that is untrue, broken, or impossible to satisfy
  as written.

## 3.18.0 — 2026-09-21
The check that guards answered questions could only ever accept one way of
writing them. Found by the first project that ever answered one.

- **`LE-28`.** `check-docs.sh` looked for the ✅ in the `###` heading and nowhere
  else. `templates/open_questions.md` said *"mark it ✅"* without saying where,
  and `templates/answered_questions.md` never mentioned it. So the natural place
  — the `**Status:**` line — produced **an answered question reported as an
  unmarked open one, forever, with nothing saying why.**
- **It took seventeen releases to surface** because the master happens to put
  its checkmarks in the heading, not by rule but because the first entry did and
  every later one copied it. **A convention that exists only as a habit in one
  file looks exactly like a documented one**, until somebody writes an entry
  from scratch.
- **The check now** parses `open_questions.md` and `answered_questions.md`
  separately and accepts a ✅ in the heading **or** on the `Status:` line.
  Verified against all three shapes, including a stray ✅ in the body of a
  genuinely open question, which must not close it.
- **A second, older bug fixed with it:** the two files were concatenated with no
  separator, so the last entry in `open_questions.md` ran on into the top of
  `answered_questions.md` and inherited its marks. Invisible, because it can
  only ever bite the final entry.
- **Both templates now say where the checkmark goes**, with an example.
- **`LE-29` — the rule an agent read and the rule that was enforced were
  maintained separately.** A role's `never: ["**"]` meant *"you do not own the
  source"* to a reader and *"you own nothing at all"* to the code, and halted a
  run 1.8 minutes in when a role wrote the directory its own prompt had just
  given it. The prompt is now **derived** from the other roles' territory
  instead of being a second hand-kept list. Same family as `LE-23`: two places
  that must agree will not, and the remedy is never *remember to update both*.

**Do:** **`check-docs.sh` is never replaced by the updater** — its gates are
yours — so this fix reaches new installs only. In an existing project, either
put the ✅ in the `###` heading (works everywhere, no code change), or copy the
`Open-question markers` block from this release's
`scripts/check-docs.sh`. You will not notice the difference until the first time
you answer a question, which is exactly when it matters.

## 3.15.0 — 2026-09-21
Every project's `CLAUDE.md` now knows when to offer a supervised agent run, and

## 3.14.0 — 2026-09-21
The supervisor exists. `bbs start "<task>"` and it runs.

- **Built at `~/Projects/ai-tools/bbs/`** — `supervisor.py` (the governor),
  `interview.py` (five questions, every answer pre-filled), `watch.py` (steps,
  choices and activities, never code), and `bbs.sh`, which is on `PATH` as
  `bbs`. Also `bbs watch`, `bbs halt` and `bbs undo`.
- **`KAM` — how easy it is to launch is part of the safety design.** The first
  draft of the guardrails told you to invoke a run by hand: open the board,
  compose a prompt per role, launch each one, register, propose, ack. It was
  correct and the owner would never have done it — *"it has to be easy to
  implement or I'll never use it."* **An unlaunched governor is not a neutral
  outcome:** it means the runs that happen are the ones hand-rolled around it,
  with no budget, no territory check and no halt. This is Rule 4 from an angle
  the framework had not considered — **a mechanism too tedious to invoke has
  the same effect as a disclaimer.**
- **All four hard stops are live**, and every one is a counter, a timer or a
  string comparison with no model in the path.
- **`LE-26` — the safety mechanism's own working files tripped the safety
  mechanism.** `.bbs/` is forbidden to every role, and is also where the
  supervisor writes its config, halt marker and report — so it halted every run
  five seconds after starting, behaving exactly as designed. Found by
  *exercising* the stops rather than reading them, along with two others,
  including a turn counter that consumed half its budget on posts from a run two

## 2.9.0 — 2026-09-19
The server finds a free port instead of failing on a collision.

  case. Until now the second one died with `OSError: [Errno 48] Address already
  in use` and a stack trace.
- **It now takes the next free port and says what held the one it wanted** — by
  project path when the holder is another Docket server, or "something that is

  started in the background — held the whole banner, including the line saying
  which port it actually chose, until the process exited.
